# ether.fi Data Catalog

A static data catalog and MCP server for ether.fi analytics datasets,
dashboards, freshness, and query-planning workflows. It helps teammates and AI
agents choose the right Dune-backed source, understand its caveats, and plan
safe, reviewable analysis.

## Live website

- Website: [https://henrystats.github.io/etherfi-data-catalog/](https://henrystats.github.io/etherfi-data-catalog/)
- Pushes to `main` enter through
  [`.github/workflows/deploy-website.yml`](.github/workflows/deploy-website.yml),
  while manual production refreshes enter through
  [`.github/workflows/studio-live-refresh.yml`](.github/workflows/studio-live-refresh.yml).
  Both call the same read-only Studio production build and Pages deployment.

## What this repo provides

- Repo-backed metadata for ether.fi analytics datasets.
- A registry of Dune dashboards and their linked datasets.
- Freshness and status views based on imported Dune results.
- A generated static website for browsing the catalog.
- Studio, an independent static analytics workspace with reusable dashboards,
  filters, metric visibility controls, and ZIP/CSV exports.
- An MCP server for catalog discovery, dashboard lookup, freshness, query
  planning, and selected live Dune-backed workflows.
- An ether.fi workflow skill pack for coordinating the catalog with Dune MCP
  and Dune Skills.

## Who it is for

- ether.fi analysts and dashboard builders.
- GTM, finance, and product teammates working with ether.fi data.
- AI agents that use MCP for dataset discovery and query planning.
- Dune users who need trusted ether.fi semantics before writing or running SQL.

## Quick start

Python 3.10 or newer is required.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e '.[dev]'
.venv/bin/python -m pytest -q
```

Run the MCP server locally over its default stdio transport:

```bash
.venv/bin/python -m etherfi_catalog.server
```

## MCP usage

The recommended public install is:

```bash
uvx --from "git+https://github.com/henrystats/etherfi-data-catalog.git" etherfi-catalog-mcp
```

The MCP server uses stdio by default. Metadata, discovery, freshness,
dashboard, and query-planning tools work without `DUNE_API_KEY`. Selected live
Dune-backed tools require `DUNE_API_KEY` in the MCP server environment when
called with `execute_live=true`; those calls may consume Dune credits.

See [MCP deployment and setup](docs/mcp_deployment.md) for client configuration,
local transport testing, secret handling, and advanced deployment notes.

## Recommended agent stack

- `etherfi-catalog` MCP: ether.fi dataset and tool selection, semantic caveats,
  freshness context, and query planning.
- Dune MCP: query execution, saved queries, results, visualizations, and
  dashboards.
- Dune Skills: Dune CLI, query-writing, optimization, and Dune-side workflow guidance for agents.
- `skills/etherfi/`: workflow instructions for combining the three layers.

Use `etherfi-catalog` to decide which ether.fi source and query shape are correct. Use Dune MCP to run, save, retrieve, visualize, and dashboard the Dune query.
For shareable charts and dashboards, confirm the catalog-vetted plan, then use Dune MCP visualization/dashboard tools.
Use Dune Skills for DuneSQL style, optimization, and Dune CLI guidance when needed.

## Website

Build the static site:

```bash
.venv/bin/python scripts/build_website.py
```

Preview the generated site at `http://localhost:8000`:

```bash
.venv/bin/python -m http.server 8000 --directory output/website
```

The build reads the repo metadata and writes `output/website`. Generated output
is ignored by git. Local builds use the checked-in previous-good Studio
snapshot unless `--studio-generated-data` selects another validated snapshot
root. Production Pages builds require the read-only `DUNE_API_KEY` repository
Actions secret and always import the latest already-stored Dune results before
they test, build, and deploy.

Studio is generated by the same command but remains separate from the dataset
catalog, MCP, and existing dashboard registry. Its local routes are:

- `http://localhost:8000/studio/`
- `http://localhost:8000/studio/kyberswap/`

The checked-in Studio snapshot is the reviewed previous-good bootstrap for a
new runner. Production ingestion copies it to an isolated temporary root before
attempting a complete live refresh; Actions never writes generated results back
to git.

The checked-in KyberSwap sample bundle remains available for offline product
review and is clearly marked as sample data. Regenerate it with:

```bash
.venv/bin/python scripts/generate_studio_demo_data.py
```

Studio also has an offline ingestion path that fetches every unique query
required by a `generated` dashboard once from deterministic fixtures, validates
a complete candidate, and atomically switches `state.json` to an immutable
snapshot. A safe local cycle is:

```bash
.venv/bin/python scripts/generate_studio_inventory.py --check
.venv/bin/python scripts/fetch_studio_data.py \
  --fixture-mode \
  --fixture-scenario success \
  --fixture-now 2026-07-31T12:00:00Z \
  --output-dir /tmp/studio-fixture-generated \
  --keep-previous 1 \
  --verbose
.venv/bin/python scripts/fetch_studio_data.py \
  --validate-only \
  --output-dir /tmp/studio-fixture-generated
.venv/bin/python scripts/build_website.py \
  --studio-generated-data /tmp/studio-fixture-generated
```

Fixture mode is offline and does not require a Dune key. The manual
[`studio-fixture-refresh.yml`](.github/workflows/studio-fixture-refresh.yml)
workflow runs directly when dispatched, does not deploy, and uploads only
short-lived diagnostics from a runner-temporary fixture directory. Production
Studio imports run on pushes to `main`, on a manual live-refresh dispatch, and
at minute 25 every four hours. All three production entry points call
[`studio-production-deploy.yml`](.github/workflows/studio-production-deploy.yml)
and require `DUNE_API_KEY` as a repository Actions secret with read access only.
The Studio schedule only imports latest stored results; Dune's independent
query schedules remain solely responsible for executing and refreshing queries.

The dashboard header's `Last Updated` value is the manifest-level
`dashboard_refreshed_at`: the UTC time when a complete Studio snapshot passed
validation and was atomically accepted for the website build. It is separate
from query execution, source-data, methodology, browser, and build timestamps.
Failed or partial attempts retain the prior successful value.

Production Studio ingestion is a read-only import, not query execution. Dune
schedules and refreshes each approved query independently; the GitHub Action
then starts one logical `GET /api/v1/query/{query_id}/results` import per unique
query, follows read-only result pages (and bounded transient GET retries) where
needed, validates the latest already-stored result, and reuses it for every
mapped metric. It records the Dune execution ID and
completion time, marks stale data without rerunning it, and preserves the
previous valid snapshot when no successful stored result is available. The
production `DUNE_API_KEY` needs read access only. Studio never uses Dune query
execution methods or stale-result auto-rerun options such as `max_age_hours`.

The KyberSwap dashboard uses only reviewed latest-result mappings. Eight summary
counters reuse one fetched result from
[Dune query 8180894](https://dune.com/queries/8180894), six Campaign Growth &
Activity charts reuse four fetched results from
[queries 8191379, 8191704, 8193003, and 8193040](https://dune.com/queries/8191379),
and the merged Capital Position & Activity section reuses two fetched results:
[Dune query 8199058](https://dune.com/queries/8199058) for the current-location
ranking and both Sankeys, and
[Dune query 8202133](https://dune.com/queries/8202133) for signed post-referral
activity. Depositor Analysis reuses that same enriched 8199058 result and
joins it, during atomic ingestion, with one fetched result apiece from
[8204345](https://dune.com/queries/8204345) and
[8204373](https://dune.com/queries/8204373). The resulting checksummed wallet
index powers rankings, concentration, tables, and investigation without any
browser-side Dune requests:

- **Campaign summary counters:** selected-period deposits, attributed TVL,
  new-depositor contribution, depositor counts, retention, and revenue;
- **Campaign Growth & Activity:** referral deposit flow plus cumulative
  deposits, attributed TVL, product/depositor breakdowns, total rankings, and
  deposit/depositor counts with prepared daily and weekly views;
- **Attributed TVL by Current Location:** attributed balances ranked by current
  protocol or destination category;
- **Post-Referral Activity:** signed daily or weekly activity grouped by label,
  project, or event;
- **Attributed Funds by Current Location:** deposited product
  (`strategy_symbol`) to attributed current token, including a synthetic
  `Exited` destination;
- **Depositor Journey:** depositor type to deposited product to
  current destination category.

All generated KyberSwap metrics now use reviewed latest-result sources. A live
refresh reads queries 8180894, 8191379, 8191704, 8193003, 8193040, 8199058,
8202133, 8204345, and 8204373 through the latest stored-result endpoint once
each, then transforms and validates each result in Python. Every live source
preserves one private raw sidecar and records
source execution and methodology provenance; the attribution source also uses
exact `Decimal` arithmetic and requires group-level and Sankey-level
reconciliation before promotion. Raw sidecars, snapshot history, attempts, and
the API key are not copied into the public website.

For a local live refresh, keep the key in the gitignored `.env` file, seed an
isolated temporary root from the checked-in previous-good snapshot, and load the
key only into the current shell process:

```bash
STUDIO_LIVE_ROOT="$(mktemp -d)"
STUDIO_LIVE_GENERATED="$STUDIO_LIVE_ROOT/studio-live-generated"
mkdir -p "$STUDIO_LIVE_GENERATED"
cp -R website/data/studio/generated/. "$STUDIO_LIVE_GENERATED/"
set -a
source .env
set +a
STUDIO_ENABLE_LIVE_DUNE=1 \
  .venv/bin/python scripts/fetch_studio_data.py \
  --output-dir "$STUDIO_LIVE_GENERATED" \
  --keep-previous 1 \
  --force \
  --verbose
.venv/bin/python scripts/fetch_studio_data.py \
  --validate-only \
  --output-dir "$STUDIO_LIVE_GENERATED"
.venv/bin/python scripts/build_website.py \
  --studio-generated-data "$STUDIO_LIVE_GENERATED"
```

This command only imports the latest results Dune has already stored. Dune's
own schedules remain solely responsible for running queries 8180894, 8191379,
8191704, 8193003, 8193040, 8199058, 8202133, 8204345, and 8204373. A valid stale
result is promoted with a stale marker and never rerun. A failed, missing, or
invalid stored result does not trigger execution and leaves the previous
validated snapshot active. Production is fail-closed: a missing secret or any
ingestion, transformation, validation, test, or build failure prevents Pages
artifact upload and deployment, so an older run cannot replace the current
valid site. The fixed production concurrency group cancels superseded runs.

See [Studio architecture and data workflow](docs/studio.md) for the registry,
snapshot, timestamp, failure, export, local-preview, and workflow contracts.
The generated [query-to-metric inventory](docs/studio-query-inventory.md) is the
reviewable mapping from dashboards and metrics to the deduplicated fetch plan.

## Freshness

Catalog freshness comes from
[Dune query 7625551](https://dune.com/queries/7625551). The importer pulls that
query's latest stored result; it does not execute the Dune SQL.

For a local refresh:

```bash
DUNE_API_KEY=... .venv/bin/python scripts/update_freshness_from_dune.py --query-id 7625551
```

The importer writes `status/dataset_freshness.yaml`. This file is a runtime
snapshot and remains gitignored; it is not source metadata. When it is absent,
the website still builds and reports unknown or undocumented runtime freshness.

The optional
[`refresh-freshness.yml`](.github/workflows/refresh-freshness.yml) workflow is
configured to run hourly or manually. With the repository's read-only
`DUNE_API_KEY` secret, it imports the stored result and uploads a short-lived
validation artifact only. It cannot build or deploy Pages, so it cannot replace
a newer live Studio deployment. Production push and manual builds import the
same catalog freshness result inside the shared production path before they
build the complete website.

## Metadata conventions

- Dataset YAML files live under `datasets/`.
- Dashboard YAML files live under `dashboards/`.
- Packaged mirrors live under `etherfi_catalog/data/datasets/` and
  `etherfi_catalog/data/dashboards/`.
- Set `show_in_core: true` when a dashboard should also appear in the website's
  Core group; do not create a separate `dashboards/core/` directory.
- Keep runtime freshness snapshots out of version control.

Metadata should document the source table, grain, refresh cadence, accuracy,
completeness, caveats, important columns, and related resources where relevant.

## Project boundaries

`etherfi-catalog` is the ether.fi semantic catalog and planning layer, not a
general-purpose Dune client. Use it for source selection, caveats, freshness,
and safe query planning. Use Dune MCP for execution, saved queries,
visualizations, and dashboard creation.
